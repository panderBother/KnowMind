# KnowMind 知识库文档增量更新与版本管理需求文档

| 项目 | 内容 |
| --- | --- |
| 文档状态 | 待评审 |
| 文档版本 | v1.0 |
| 创建日期 | 2026-09-26 |
| 目标模块 | 文档上传、解析入库、向量索引、全文索引、知识库检索 |
| 优先级 | P0：更新正确性；P1：增量成本优化；P2：外部数据源同步 |

## 1. 背景

KnowMind 当前支持向知识库上传文档、解析切块并写入向量索引与全文索引。现有实现具备以下基础能力：

- 上传时按知识库内文件原始内容的 MD5 判断完全重复文件，重复时跳过。
- 每个文档维护 `DocumentChunk` 清单，并根据页码和文本计算 Chunk Hash。
- 同一文档重新索引时，可复用 Hash 未变化的 Chunk，仅为新增或变化的 Chunk 生成 Embedding。
- 可从 Chroma/Milvus、Whoosh 中删除失效 Chunk。

但当前“上传新文档”和“更新已有文档”的产品语义尚未分开：

- 同名但内容不同的文件会新增为另一份文档，不会替换旧文档。
- 用户无法在上传时明确选择“新增”或“更新已有文档”。
- 后端虽然已有文档重新索引能力，前端尚无面向已完成文档的“上传新版本”入口。
- 文档、向量索引、全文索引分属不同存储，更新过程中缺少原子切换，失败时可能出现部分更新。
- Chunk Hash 没有区分文本、元数据和处理配置；切块参数或 Embedding 模型改变时，可能错误复用旧结果。
- 文档更新没有版本历史，无法查看、回滚或保留一次失败更新的上下文。

因此需要建立明确、可恢复、可审计的文档更新机制，同时保留现有 Chunk 级增量计算优势。

## 2. 目标

本需求的目标是建立以下统一规则：

1. 使用稳定的 `document_id` 表示“同一份逻辑文档”。
2. 每次更新产生独立 `revision_id`，旧版本在新版本成功前继续可用。
3. 使用内容 Hash 判断是否发生变化，而不是依赖文件名判断文档身份。
4. 只为真正变化且无法复用的 Chunk 重新生成 Embedding。
5. 新版本完整构建并验证成功后，一次性切换为当前版本。
6. 删除、失败、重试和并发更新均可恢复，不向检索暴露半成品或孤儿索引。
7. 为未来目录、网盘等外部数据源的自动同步预留稳定的来源标识。

## 3. 非目标

本期不包含：

- 多人同时在线编辑同一文档正文。
- 文档内容的逐字符 diff 展示。
- Git 式分支、合并与冲突解决。
- 跨知识库自动合并相似文档。
- 第一阶段直接引入 Kafka、CDC 或独立工作流平台。
- 对所有历史文档立即执行全量重新 Embedding。

## 4. 核心定义

### 4.1 逻辑文档 Document

用户在知识库中看到和管理的文档实体。逻辑文档拥有稳定的 `document_id`，文件名、内容、存储地址和索引版本均可变化。

### 4.2 文档版本 Document Revision

文档每次上传或更新产生的不可变版本。每个版本拥有独立的原始文件、解析结果、处理配置指纹和状态。

### 4.3 当前版本 Current Revision

逻辑文档当前对搜索、RAG 和引用可见的版本，由 `documents.current_revision_id` 指向。

### 4.4 来源标识 Source Key

外部数据源中稳定标识一份文件的键，例如网盘文件 ID。文件改名或移动目录后，`source_key` 仍应保持不变。

### 4.5 处理管线指纹 Pipeline Fingerprint

影响解析、切块、向量或检索结果的配置摘要，至少包含：

- 解析器名称和版本。
- OCR/VLM 引擎与关键配置。
- 切块算法版本、最小/最大长度、重叠大小。
- Embedding 提供方、模型、维度和归一化方式。
- 参与检索的元数据 Schema 版本。

## 5. 总体方案

采用“版本化构建、增量计算、原子激活、异步清理”的更新模型：

```text
上传新版本
  ↓
创建 pending revision，当前版本继续提供检索
  ↓
解析、切块、计算差异
  ↓
复用已有向量，仅计算变化 Chunk
  ↓
将新版本完整写入向量索引和全文索引
  ↓
校验新版本完整性
  ↓
数据库事务切换 current_revision_id
  ↓
异步清理旧版本索引和过期文件
```

数据库是文档版本可见性的事实源。向量索引和全文索引中的记录必须携带 `document_id`、`revision_id` 和生命周期状态；检索结果只有在版本与数据库当前版本一致时才能进入最终召回结果。

## 6. 用户场景与交互需求

### 6.1 上传新文档

用户从知识库上传区选择文件时，默认动作是“新增文档”。

- 文件内容与当前知识库某文档完全一致：不重复入库，提示“该文件已存在”，并提供查看已有文档入口。
- 文件名相同但内容不同：不得自动覆盖，应提示用户选择：
  - 更新已有文档，推荐用于同一资料的新版本。
  - 作为新文档上传，适用于只是同名的不同资料。
- 文件名不同但内容完全一致：仍视为完全重复，可提示已有文档名称并跳过。

### 6.2 更新已有文档

文档列表和文档详情提供“上传新版本”操作。

- 用户先选定逻辑文档，再上传一个文件。
- 更新沿用原 `document_id`，创建新的 `revision_id`。
- 更新过程中显示：“新版本处理中，当前仍使用 vN”。
- 成功后显示新版本号、更新时间和增量处理统计。
- 失败后旧版本继续可检索，并显示失败原因和“重试”入口。

### 6.3 完全相同版本

用户上传的文件 SHA-256 与当前版本一致时：

- 不创建新的有效版本。
- 不触发解析、切块或 Embedding。
- 返回“内容未变化”。
- 可记录一次审计事件，但不得增加版本号和文档计数。

### 6.4 查看版本历史

文档详情提供版本历史，至少显示：

- 版本号。
- 文件名和文件大小。
- 上传时间与上传者。
- 状态：处理中、当前版本、历史版本、失败、已清理。
- Chunk 总数、新增数、变化数、复用数、删除数。
- 处理配置摘要。

### 6.5 回滚版本

用户可以把仍保留完整文件与索引的历史版本设为当前版本。

- 可直接激活的版本无需重新解析。
- 索引已经清理的版本需要重新构建后才能激活。
- 回滚也应形成审计记录。
- 回滚失败时保持原当前版本不变。

### 6.6 删除文档

用户删除文档后应立即从检索结果中消失，但物理数据异步清理：

1. 数据库事务将文档标记为 `deleted`。
2. 搜索和 RAG 立即过滤该文档。
3. 后台删除向量、全文索引、版本记录和原始文件。
4. 清理完成后标记为 `purged`。
5. 清理失败自动重试，失败期间也不得再次被检索到。

## 7. 文档身份与重复判断规则

### 7.1 手工上传

- `document_id` 由“新增”或用户明确选定的“更新目标”决定。
- 文件名只用于展示和候选提示，不能作为自动覆盖依据。
- 内容 Hash 只用于判断内容是否相同，不能代替逻辑文档身份。

### 7.2 外部数据源同步

未来接入外部数据源时，文档身份由以下联合键确定：

```text
knowledge_base_id + source_type + source_key
```

- 相同联合键：更新原逻辑文档。
- 新联合键：新增文档。
- 原联合键在一次权威同步中消失：进入软删除流程。
- 文件路径和文件名变化只更新元数据，不创建新逻辑文档。

### 7.3 Hash 算法

新数据统一使用 SHA-256。为兼容现有数据，可以保留原 MD5 字段进行只读迁移，但新增判断不得继续依赖 MD5。

## 8. 增量判定规则

应拆分以下指纹，避免把不同变化混为一类：

| 指纹 | 组成 | 作用 |
| --- | --- | --- |
| `source_sha256` | 原始文件字节 | 判断完全相同文件 |
| `extracted_text_sha256` | 标准化后的完整解析文本 | 判断文件变化是否影响正文 |
| `content_hash` | 标准化后的 Chunk 文本 | 判断能否复用语义向量 |
| `metadata_hash` | 页码、标题、层级、ACL、来源等检索元数据 | 判断是否只需更新元数据 |
| `vector_fingerprint` | `content_hash` + Embedding 配置指纹 | 判断向量能否复用 |
| `pipeline_fingerprint` | 解析、OCR、切块、Embedding、Schema 配置 | 判断需要重跑哪些阶段 |

### 8.1 决策矩阵

| 条件 | 处理方式 |
| --- | --- |
| `source_sha256` 相同 | 完全跳过 |
| 原文件不同，但解析全文和管线指纹相同 | 保存必要的文件元数据；索引不变 |
| Chunk 文本与向量指纹相同，元数据相同 | 复用向量和索引记录 |
| Chunk 文本相同，元数据变化 | 复用向量，仅更新检索元数据 |
| Chunk 文本新增或变化 | 生成 Embedding 并 upsert |
| 旧 Chunk 未被新版本匹配 | 新版本激活后异步删除 |
| Embedding 模型或维度变化 | 全部重新生成向量 |
| 切块算法或切块参数变化 | 全文重新切块，再执行 Chunk 差量匹配 |
| 解析器/OCR 配置变化 | 重新解析，再执行切块与差量匹配 |
| 仅 ACL、生命周期变化 | 不重新 Embedding，只更新过滤元数据 |

### 8.2 Chunk 匹配

- 对新版本的 Chunk 按 `content_hash` 匹配旧版本 Chunk。
- 重复文本使用出现序号或稳定上下文辅助匹配，保证一个旧 Chunk 只能复用一次。
- 文本相同但顺序变化时允许复用向量。
- 页码或标题变化不得强制重新 Embedding，但需要更新元数据。
- 新 Chunk ID 必须可确定性生成，确保后台任务重复执行时结果幂等。

### 8.3 Embedding 缓存

P1 阶段增加 Embedding 缓存，缓存键为 `vector_fingerprint`。

- 同一文本、同一 Embedding 配置只生成一次向量。
- 不同文档之间是否允许共享缓存由部署配置决定。
- 缓存不得跨不同模型、维度或归一化配置复用。

## 9. 一致性与原子切换

### 9.1 基本要求

- 新版本未完成前，旧版本必须保持可检索。
- 不允许先删除旧索引再构建新索引。
- 新版本不得在未激活时进入最终搜索结果。
- 版本激活必须以数据库事务更新 `current_revision_id` 为准。
- 向量索引和全文索引写入必须使用相同 `revision_id`。

### 9.2 检索过滤

索引候选记录至少携带：

- `kb_id`
- `user_id`
- `document_id`
- `revision_id`
- `chunk_id`
- `lifecycle_status`

搜索服务返回最终结果前，应校验：

1. 文档未删除且处于可检索状态。
2. 候选结果的 `revision_id` 等于文档 `current_revision_id`。
3. Chunk 生命周期允许被检索。

旧版本索引即使尚未物理删除，也必须因版本不匹配而被过滤。

### 9.3 激活前校验

至少完成以下校验后才允许激活：

- 解析内容非空。
- 数据库 Chunk 数量与计划数量一致。
- 向量索引成功写入预期 Chunk。
- 全文索引成功写入预期 Chunk。
- 所有 Chunk 使用相同 `document_id` 和 `revision_id`。
- Embedding 向量维度与当前索引配置一致。

## 10. 状态模型

### 10.1 文档版本状态

```text
pending → parsing → chunking → embedding → indexing → validating → active
    └────────────────────────────────────────────────────────────→ failed

active → superseded → purged
failed → pending（重试）
```

### 10.2 约束

- 一个逻辑文档最多只能有一个 `active` 版本。
- 同一逻辑文档同一时间只允许一个更新任务进入处理阶段。
- 并发更新请求返回冲突提示，或明确排队，不得同时覆盖。
- `failed` 版本不得成为 `current_revision_id`。
- `superseded` 版本在保留期内可用于回滚。

## 11. 幂等、重试与并发控制

- 每次更新生成唯一 `ingest_job_id`。
- 同一更新任务重试时必须沿用相同 `revision_id` 和确定性 Chunk ID。
- 对 `document_id + source_sha256 + pipeline_fingerprint` 建立幂等约束，避免重复任务。
- 文档更新使用乐观锁版本号或数据库行锁，防止并发激活。
- upsert、删除和状态推进均必须允许安全重试。
- 已激活版本的重复完成消息不得再次增加知识库文档计数。
- 任务超时后可由恢复任务重新投递，不得永久停留在 `processing`。

## 12. 数据模型需求

### 12.1 documents

建议新增或调整字段：

- `current_revision_id`
- `source_type`
- `source_key`
- `lifecycle_status`
- `deleted_at`
- `lock_version`

`documents` 保留逻辑文档级名称、归属、权限和当前版本指针。

### 12.2 document_revisions

建议新增表，字段至少包括：

- `id`
- `document_id`
- `revision_no`
- `filename`
- `storage_key`
- `file_bytes`
- `source_sha256`
- `extracted_text_sha256`
- `pipeline_fingerprint`
- `parsed_content`
- `parsed_title`
- `parsed_summary`
- `status`
- `chunk_count`
- `added_chunk_count`
- `changed_chunk_count`
- `reused_chunk_count`
- `removed_chunk_count`
- `error_message`
- `created_by`
- `created_at`
- `activated_at`

### 12.3 document_chunks

建议增加：

- `revision_id`
- `metadata_hash`
- `vector_fingerprint`
- `lifecycle_status`

唯一约束至少覆盖：

- `revision_id + ordinal`
- `chunk_id`

### 12.4 ingest_jobs

建议新增任务记录，保存：

- 任务类型与状态。
- `document_id`、`revision_id`。
- 当前阶段和进度。
- 尝试次数、下次重试时间。
- 输入摘要、错误信息和处理统计。
- 创建、开始、完成时间。

## 13. API 需求

API 的具体 URL 可在技术设计阶段确认，但应具备以下语义：

### 13.1 新增文档

- 创建新的逻辑文档及首个版本。
- 返回 `document_id`、`revision_id`、任务 ID 和是否命中重复文件。

### 13.2 上传新版本

- 请求必须明确携带目标 `document_id`。
- 创建新版本，不覆盖当前版本的原始文件和解析结果。
- 返回异步任务状态。

### 13.3 查询更新状态

- 返回当前阶段、进度、统计、失败原因。
- 明确告知当前仍在使用哪个版本。

### 13.4 查询版本历史

- 分页返回版本列表和增量统计。

### 13.5 激活或回滚版本

- 仅允许激活校验通过的版本。
- 返回新的当前版本。

### 13.6 删除文档

- 首先执行逻辑删除并返回成功。
- 物理清理由后台任务完成。

## 14. 索引对账与自动修复

增加周期性对账任务，数据库作为事实源，检查：

- 当前版本数据库 Chunk 存在但向量索引缺失。
- 当前版本数据库 Chunk 存在但全文索引缺失。
- 索引中存在无对应数据库记录的孤儿 Chunk。
- 索引记录指向非当前版本但仍标记为可检索。
- 数据库、向量索引、全文索引的 Chunk 数量不一致。
- 长时间停留在处理中状态的任务。

修复策略：

- 缺失记录：按版本重新补写。
- 孤儿记录：确认不属于活动任务后删除。
- 状态异常：先从检索中过滤，再重建或清理。
- 无法自动修复：记录告警并提供人工重建入口。

## 15. 监控与审计

### 15.1 指标

至少记录：

- 上传和更新成功率。
- 各处理阶段耗时。
- 新增、变化、复用、删除 Chunk 数量。
- Embedding 调用量与复用率。
- 索引写入失败率。
- 更新失败但旧版本继续服务的次数。
- 对账发现的缺失与孤儿索引数量。
- 删除清理积压数量。

### 15.2 审计事件

至少记录：

- 新增文档。
- 上传新版本。
- 激活版本。
- 回滚版本。
- 删除和恢复文档。
- 手动重新索引。
- 自动修复索引。

## 16. 权限与安全

- 仅拥有知识库编辑权限的用户可以新增、更新、回滚或删除文档。
- 更新版本不得绕过原文档的知识库归属和用户隔离。
- 原始文件和版本下载必须继续经过鉴权。
- 索引元数据必须包含用户和知识库隔离字段。
- 文件校验、大小限制、格式白名单和恶意内容防护沿用现有上传安全策略。
- 软删除期间不得通过直接文档接口、搜索或引用接口访问已删除内容。

## 17. 兼容与迁移

- 现有每个文档迁移为一个逻辑文档和一个初始版本。
- 现有 `documents.storage_key`、解析字段和 Hash 数据迁移到首个 `document_revision`。
- 现有 `document_chunks` 关联到对应初始版本。
- 现有向量和 Whoosh 元数据补充 `revision_id`；无法原地补充时按文档渐进重建。
- 迁移期间同时兼容无 `revision_id` 的旧索引记录，但旧兼容逻辑应设置下线期限。
- 迁移不得要求一次性重建全部知识库；允许按访问或后台任务逐步迁移。

## 18. 验收标准

### 18.1 上传与身份

- [ ] 上传新文件不会覆盖知识库中其它文档。
- [ ] 完全相同文件不会重复解析或增加文档计数。
- [ ] 同名不同内容必须由用户明确选择新增或更新。
- [ ] 更新已有文档沿用原 `document_id` 并产生新 `revision_id`。

### 18.2 可用性与一致性

- [ ] 新版本处理期间，旧版本仍可正常检索。
- [ ] 新版本失败后，旧版本继续作为当前版本。
- [ ] 向量索引写入失败或全文索引写入失败时不得激活新版本。
- [ ] 激活后检索只返回当前版本 Chunk。
- [ ] 更新过程任何阶段重试均不会产生重复可见 Chunk。

### 18.3 增量处理

- [ ] 完全未变化的 Chunk 不调用 Embedding。
- [ ] 仅页码、标题或 ACL 变化时不重新生成向量。
- [ ] 新增或修改的 Chunk 正确生成并写入新向量。
- [ ] 已删除 Chunk 在新版本激活后不再参与检索。
- [ ] Embedding 模型、维度或切块配置改变时能触发正确范围的重建。

### 18.4 删除与恢复

- [ ] 逻辑删除成功后文档立即无法被搜索和引用。
- [ ] 物理清理失败可自动重试且不会使文档重新可见。
- [ ] 对账任务能识别并修复缺失索引。
- [ ] 对账任务能识别并清理孤儿索引。

### 18.5 版本历史

- [ ] 用户可以查看版本列表和每次处理统计。
- [ ] 用户可以回滚到仍可用的历史版本。
- [ ] 回滚失败不会影响原当前版本。

## 19. 测试范围

至少覆盖：

- 同文件同名、同文件异名、同名异内容。
- 新增、更新、失败、重试、回滚、删除。
- 单 Chunk 修改、头部插入、尾部删除、页面移动、重复段落。
- 切块参数变化、Embedding 模型变化、仅元数据变化。
- Chroma 成功但 Whoosh 失败，以及相反情况。
- Worker 在解析、Embedding、索引写入、激活前后异常退出。
- 同一文档并发提交两个新版本。
- 重复投递同一后台任务。
- 大文档和批量文档下的处理时间、内存和索引写入量。
- 旧数据迁移与新旧索引兼容。

## 20. 分阶段实施建议

### P0：更新正确性

- 区分“新增文档”和“上传新版本”。
- 引入文档版本和 `current_revision_id`。
- 新增版本化状态机与任务状态。
- 使用 SHA-256 判断完全重复。
- 实现旧版本持续服务、成功后切换。
- 检索过滤非当前版本和已删除文档。
- 删除调整为先逻辑删除、后物理清理。

### P1：增量成本优化

- 拆分文本 Hash、元数据 Hash 和向量指纹。
- 引入处理管线指纹。
- 完善 Chunk 差量分类。
- 增加 Embedding 缓存。
- 增加索引对账和自动修复。
- 增加版本历史和回滚。

### P2：数据源同步

- 引入 `source_type + source_key`。
- 支持基于更新时间水位的周期同步。
- 支持权威同步中的删除检测。
- 支持目录移动、文件改名和权限变化。

## 21. 方案约束与明确决策

本需求明确不采用以下方式：

- 不按文件名自动覆盖。
- 不在新版本构建成功前删除旧索引。
- 不把向量数据库作为文档状态的事实源。
- 不仅根据 Chunk 文本 Hash 判断所有类型的变化。
- 不因一次文件更新而重建整个知识库。
- 不允许失败任务留下可被检索的半成品版本。
